Below is the Replit-ready spec. This is tighter than the earlier version and includes the exact Cybersource credential requirements, provider model, UI behavior, server signing requirements, and acceptance rules.

Payments P3 — Cybersource Provider Settings
Build Cybersource Provider Settings inside the existing /admin/payments Superadmin dashboard.

This must sit beside Authorize.net in the same Payments area. It is not a replacement for Authorize.net.

Official Cybersource REST credentials are different from Authorize.net:

Merchant ID
API Key ID
Shared Secret / Secret Key
optional Organization ID or Portfolio ID for meta-key / portfolio setups
Environment: test or production
Cybersource REST hosts:

test: apitest.cybersource.com
production: api.cybersource.com
Cybersource REST HTTP Signature requests require:

v-c-merchant-id
host
date
(request-target)
digest for POST/PUT requests
Signature header using keyid, algorithm="HmacSHA256", signed with the Shared Secret
Sources:

Cybersource API keys
Cybersource HTTP Signature auth
Cybersource meta keys
Goal
Superadmin can configure, test, clear, and audit Cybersource credentials directly from the OKÜ admin website, using the same encrypted credential pattern already created for Authorize.net.

The user experience should feel like:

Admin Console → Payments → Cybersource

Not a developer diagnostics page.

Schema
First inspect what Authorize.net P1 created.

If there is already a generic encrypted gateway settings model, reuse it.

If there is an Authorize.net-specific model, migrate toward a generic provider model instead of adding another one-off Cybersource model.

Recommended Prisma shape:

enum PaymentGatewayProvider {
  AUTHORIZE_NET
  CYBERSOURCE
}

enum PaymentGatewayEnvironment {
  SANDBOX
  TEST
  PRODUCTION
}

model PaymentGatewaySettings {
  id                       String                 @id @default(cuid())
  provider                 PaymentGatewayProvider @unique
  enabled                  Boolean                @default(false)
  environment              String                 @default("test")

  encryptedCredentialsJson Json?
  publicSettingsJson       Json?

  lastTestStatus           String?
  lastTestMessage          String?
  lastTestedAt             DateTime?

  createdAt                DateTime               @default(now())
  updatedAt                DateTime               @updatedAt
}
If the existing model has different names, adapt to it. The important rule is:

secrets go in encrypted credential storage
non-secrets go in public/settings JSON
never store secrets in CommerceSettings

Encryption
Reuse the existing Authorize.net encryption helper.

Requirements:

encryption key comes from APP_ENCRYPTION_KEY
use AES-256-GCM, same pattern as Authorize.net
if APP_ENCRYPTION_KEY is missing:
GET still works
status says credential editing unavailable

if decryption fails:
mark DB credentials unusable
do not crash the Payments page
surface warning:
Saved Cybersource credentials cannot be decrypted. Check APP_ENCRYPTION_KEY.

HTTP Signature Helper
Implement server-side signing only.

Function shape:

type CybersourceSignatureInput = {
  method: "GET" | "POST" | "PUT" | "DELETE";
  path: string;
  body?: string;
  merchantId: string;
  keyId: string;
  sharedSecret: string;
  host: string;
};

function buildCybersourceHttpSignatureHeaders(input: CybersourceSignatureInput): Record<string, string>
For POST/PUT:

include Digest
include headers list:
host date (request-target) digest v-c-merchant-id
For GET/DELETE:

no digest unless Cybersource endpoint requires it
include headers list:
host date (request-target) v-c-merchant-id
Signature algorithm:

HMAC-SHA256
decode Cybersource shared secret from base64 if Cybersource key is base64 encoded
output base64 signature
Header example:

v-c-merchant-id: {merchantId}
host: apitest.cybersource.com
date: Wed, 06 May 2026 15:00:00 GMT
digest: SHA-256={base64Digest}
signature: keyid="{keyId}", algorithm="HmacSHA256", headers="host date (request-target) digest v-c-merchant-id", signature="{signature}"
Test Connection
Implement:

POST /api/v1/admin/payments/cybersource/test
Rules:

must not charge a card
must not authorize a payment
must use selected environment host
must use saved encrypted DB credentials first
may fall back to env only if that is already the Authorize.net pattern
Preferred approach:

Use a safe Cybersource endpoint that validates authentication without creating money movement.

If a true no-op auth endpoint is unavailable in the repo/timebox, implement a signed GET request to a harmless endpoint that Cybersource will authenticate before returning either a valid response or a non-auth business response. Treat:

2xx as pass
401 / 403 as credential failure
network/DNS as connection failure
other signed response as “credentials accepted but endpoint returned X” only if clearly authenticated
Do not use /pts/v2/payments with a real auth/capture in the test button.

Provider Architecture
If no shared adapter exists, add a small interface now but only implement what is needed.

export type PaymentProviderId = "AUTHORIZE_NET" | "CYBERSOURCE";

export type PaymentProviderStatus = {
  provider: PaymentProviderId;
  enabled: boolean;
  configured: boolean;
  environment: string;
  credentialSource: "database" | "environment" | "none";
  lastTestStatus?: "passed" | "failed";
  lastTestedAt?: string;
};

export interface PaymentProviderAdapter {
  provider: PaymentProviderId;
  getStatus(): Promise<PaymentProviderStatus>;
  testConnection(): Promise<{ ok: boolean; message: string; rawCode?: string }>;

  // Future only. Do not wire Cybersource checkout in this task.
  charge?: unknown;
  refund?: unknown;
  void?: unknown;
}

One Implementation Note
Because some Cybersource account setups use meta keys at the portfolio or organization level, keep organizationId and portfolioId optional now. The critical runtime credential set is still:

merchantId
keyId
sharedSecret
environment
That gives OKÜ the right Superadmin control now without overbuilding the full Cybersource payment engine before launch.
