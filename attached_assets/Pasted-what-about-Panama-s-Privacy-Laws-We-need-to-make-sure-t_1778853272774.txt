I checked current Panama privacy sources. The governing framework is Law 81 of March 26, 2019, regulated by Executive Decree 285 of May 28, 2021. ANTAI is the supervisory authority. The law applies to databases in Panama, Panama-domiciled controllers, data originating/stored in Panama, and internet/digital commercial activity aimed at Panama. Sources:

Panama Privacy Principles To Design Around
Panama’s Law 81 framework is broadly aligned with modern privacy principles:

lawful basis / consent where needed
purpose limitation
proportionality / data minimization
transparency
data accuracy
confidentiality
security
retention limitation
data subject rights: access, rectification, cancellation/deletion, opposition, portability
accountability of the data controller/custodian
regulated transfers to third parties and cross-border processors
ANTAI also states it can investigate and sanction violations. DLA Piper notes sanctions may range from USD 1,000 to USD 10,000 depending on severity. More importantly, the reputational harm would be much larger.

What This Means For OKÜ
Treat the platform as having four privacy zones:

Public / low-risk
Names, public profiles, venues, event pages.

User account / medium-risk
Email, phone, bookings, ticket history, referrer code.

Financial / high-risk
commissions, payout status, payment provider references, order history.

Restricted compliance / highest-risk
bank account numbers, ID/tax/RUC, proof of address, source-of-funds status, bank readiness, compliance notes.

Banking/KYC data must live in zone 4.

Non-Negotiable Product Rules

No raw bank data after save
Account numbers, IDs, tax numbers, RUCs should never be returned to the browser after save. Only masked values.

Encryption is mandatory
Sensitive beneficiary fields must use APP_ENCRYPTION_KEY. If the key is missing, saving is blocked.

Need-to-know access
Referrers can see their own masked profile. Admin Commercial can maybe see payout readiness, not raw compliance detail. ADMIN_FINANCE + SUPERADMIN review beneficiary records.

No documents until storage is airtight
For P1, use document status flags and finance notes. Add uploads later only with private storage, signed URLs, retention rules, malware scanning, and access audit.

Privacy notice before collection
Before collecting beneficiary info, show a short privacy notice:
“We collect this information only to verify payout eligibility and process bank payouts. Sensitive values are encrypted and shown only in masked form after save.”

Right to access / correct / delete
Build an admin workflow to export a user’s personal data, correct it, and deactivate/delete where legally possible. Some financial records must be retained for accounting/audit, but the UI should explain that.

Purpose-limited internal visibility
Staff scanners do not need payout data. Referrers do not need bank export details. Commercial admins do not need tax IDs.

Bank-readiness is not bank KYC
OKÜ can record “OKÜ verified” and “bank-ready,” but should not claim Banesco KYC approval unless Banesco provides that status.

Technical Controls
Implement or verify:

AES-256-GCM encryption for bank/ID/tax fields
separate encryption helper for beneficiary data
no raw secrets or PII in AuditLog metadata
strict masking helpers
role-based field-level access
audit log for every sensitive view/update
rate limiting on beneficiary/profile endpoints
CSRF protection on profile updates
session timeout for finance/admin users
2FA for Superadmin and Admin Finance if available
encrypted backups
database access restricted to production operators only
no PII in logs, analytics, Sentry, error capture, or console output
private document storage later, not public URLs
retention/deletion policy by data class

Retention Policy
Suggested:

Public account profile: while account active
Bookings/orders/tickets: accounting/legal retention period
Payment gateway references: accounting/legal retention period
Bank account encrypted values: while payout relationship active + retention window
Rejected beneficiary profiles: limited retention, e.g. 12-24 months unless dispute
Raw uploaded documents later: shortest practical window
Audit logs: long retention, but never raw sensitive data
Confirm exact periods with Panama counsel/accountant.

Best Replit Master Prompt
Use this after the payout architecture task, or attach it as a privacy hardening layer:

Implement Privacy & Compliance P0 for beneficiary, payout, and financial data.

Goal:
Ensure OKÜ’s payout, beneficiary verification, and financial workflows comply with Panama’s Law 81 personal data protection framework and are designed to make users feel safe.

Context:
OKÜ collects personal, financial, and bank-readiness information for referrers, influencers, partners, hosts, vendors, and staff incentives. Banking/KYC-related fields are high-risk and must be protected with stronger controls than ordinary profile data.

Legal framing:
Panama Law 81 and Executive Decree 285 require lawful, transparent, proportional, secure, purpose-limited processing of personal data, with data subject rights and accountability. Do not treat OKÜ as the bank’s KYC authority. OKÜ records beneficiary verification and bank-readiness; Banesco remains responsible for formal banking/KYC requirements.

Implement:

1. Data classification
Create a documented data classification map:
- PUBLIC
- INTERNAL
- FINANCIAL
- RESTRICTED_COMPLIANCE

Classify beneficiary bank data, ID/tax/RUC, source-of-funds status, compliance notes, and document statuses as RESTRICTED_COMPLIANCE.

2. Field-level access control
Restrict restricted compliance fields:
- SUPERADMIN: full access
- ADMIN_FINANCE: review access
- ADMIN_COMMERCIAL: readiness summary only
- earners: own masked data only
- staff/hosts: no access

3. Sensitive data protection
- Encrypt bank account, ID, tax/RUC fields using APP_ENCRYPTION_KEY.
- Block saves if APP_ENCRYPTION_KEY is missing.
- Never return raw sensitive values after save.
- Mask all sensitive values in UI.
- Never write raw sensitive data to AuditLog, error logs, analytics, or Sentry/error capture.

4. Sensitive access audit
Create audit events for:
- beneficiary.sensitive.viewed
- beneficiary.sensitive.updated
- beneficiary.profile.submitted
- beneficiary.profile.approved
- beneficiary.profile.rejected
- beneficiary.profile.hold
- payout.bank_export.generated
Do not include raw sensitive values in metadata.

5. Privacy notices
Add clear notices before beneficiary data collection:
“OKÜ uses this information only to verify payout eligibility and process bank transfers. Sensitive values are encrypted and shown only in masked form after saving.”

Add admin warning:
“Restricted compliance data. Access to this record is logged.”

6. Data subject request workflow
Create /admin/privacy/requests:
Request types:
- ACCESS
- RECTIFICATION
- CANCELLATION
- OPPOSITION
- PORTABILITY
- DEACTIVATION
- BANK_DETAIL_CORRECTION

Statuses:
- RECEIVED
- VERIFYING_REQUESTER
- IN_REVIEW
- COMPLETED
- DENIED

Allow admin to log requests and outcomes.

7. Vendor / processor register
Create /admin/privacy/vendors:
Track:
- vendor name
- purpose
- data categories shared
- country/location
- DPA/contract status
- retention notes
- risk level

Seed entries:
- Replit/hosting
- database provider
- Resend
- Cybersource
- Banesco
- object storage if used
- error monitoring if used

8. Retention policy metadata
Create retention categories for:
- accounts
- bookings/orders/tickets
- payment references
- beneficiary profiles
- bank details
- rejected verification records
- audit logs
- future uploaded documents

Do not auto-delete yet unless already safe. Show policy metadata and prepare for future deletion workflows.

9. UI trust layer
Add safety cards on beneficiary/referrer/partner payout screens:
- Bank payouts only
- Encrypted sensitive fields
- Masked after save
- Finance review required
- Audit trail enabled

10. Security guardrails
- Rate-limit beneficiary profile endpoints.
- Require authenticated session.
- Require server-side permission checks.
- No restricted fields in client bundles.
- No restricted fields in search indexes.
- No restricted fields in CSV exports except bank export adapters explicitly allowed for finance.

Acceptance:
- Restricted payout/KYC fields are encrypted and masked.
- Users see clear privacy notices before submitting bank data.
- Finance/admin access to sensitive data is role-gated and audit-logged.
- Admin has a privacy request register.
- Admin has a vendor/processor register.
- No raw bank/ID/tax data appears in AuditLog or API responses.
- Existing payout and commission logic is unchanged.
- Existing checkout/payment gateway logic is unchanged.
- Dev compile passes.
My blunt recommendation: do this before collecting real bank or ID information. You can launch customer checkout before it is perfect, but do not launch beneficiary banking collection without this layer.
