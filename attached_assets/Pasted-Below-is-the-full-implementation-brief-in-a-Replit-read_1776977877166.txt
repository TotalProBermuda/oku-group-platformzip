Below is the full implementation brief in a Replit-ready style.

Task: Partner-Managed Co-Host Invite Seats
1. Overview
What this is

Replace the current co-host creation flow, which requires an already-registered user, with an invite-based seat model that allows a partner to invite a co-host by email, assign scoped permissions to a specific event or series, and let that person create or link an account through the acceptance flow.

Why this matters

The existing flow creates friction and blocks partner-led collaboration. Hospitality partners need to be able to quickly invite sommeliers, guest-list managers, brand reps, temporary hosts, and other collaborators without admin intervention or a prerequisite account.

This change introduces a partner-driven growth loop:

Partner creates a seat
Invite is sent by email
Invitee accepts and completes account setup
Access is granted only to the assigned scope
No platform admin required for standard onboarding
2. Problem Statement
Current issue

Today, when a partner tries to add a co-host, the system checks for an existing user account tied to that email. If none exists, the operation fails with:

"No user found for that email. Ask them to create an account first, then add them as a co-host."

Why this is bad

This creates several problems:

unnecessary bottleneck
poor partner UX
admin dependency
lost invitations / delayed event setup
weak virality and poor seat-led platform growth
Desired behavior

A partner should be able to:

enter a co-host name and email
assign a role and scope
send an invite even if no account exists
see the seat as pending
resend or revoke the invite
have the invitee create or link an account via invite acceptance
activate access only for the intended event or series
3. Product Goal

Enable Partner-Managed Invite Seats so that:

a partner can create a co-host seat by email,
the seat can exist before a user account exists,
the invitee can accept the invite and onboard,
the resulting account is linked to the specific assigned event or series,
permissions remain tightly scoped and do not grant broader admin rights.
4. Scope
In Scope
invite co-host by email without pre-existing user account
create pending seat records
send invite email with secure token
accept invite via sign-up or sign-in flow
bind accepted user account to seat
grant scoped access to event or series
partner ability to resend or revoke pending invites
display pending and active co-host seats in dashboard
preset role templates for MVP
audit trail for invite lifecycle
token expiry handling
email-match enforcement for acceptance
Out of Scope for MVP
custom permission builder UI
bulk invite import
invite by SMS/WhatsApp
organization/team hierarchy beyond seat scope
account merge flows
accepting invite with a different email and later reconciling it
partner-level permanent staff access across all future events
delegated billing/payout management
SCIM / SSO provisioning
5. User Stories
Primary

As a partner, I want to invite a co-host by email even if they do not yet have an account, so I can set up event collaborators quickly.

As an invitee, I want to accept my invite, create or sign into my account, and be taken directly to the event I was invited to support.

As a product/admin team, I want all co-host access to be scoped and auditable so platform security remains intact.

Secondary

As a partner, I want to see which co-host invites are pending, active, expired, or revoked.

As a partner, I want to resend an invite if someone missed the email.

As a partner, I want to revoke an invite before it is accepted.

6. Core Product Model

The system must distinguish between:

Seat = invitation + permission container
User = platform account
Access Grant = actual permission link once accepted
Principle

A seat may exist without a user.
A user may later claim a seat.
Permissions are activated only after claim/acceptance.

7. Data Model / Schema
7.1 partner_seats

Represents the partner-created seat assignment.

CREATE TABLE partner_seats (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  partner_id UUID NOT NULL REFERENCES partners(id) ON DELETE CASCADE,
  created_by_user_id UUID NOT NULL REFERENCES users(id),
  event_id UUID NULL REFERENCES events(id) ON DELETE CASCADE,
  series_id UUID NULL REFERENCES event_series(id) ON DELETE CASCADE,

  invited_name VARCHAR(255) NULL,
  invited_email CITEXT NOT NULL,
  role_code VARCHAR(100) NOT NULL,
  status VARCHAR(50) NOT NULL DEFAULT 'invited',

  permissions_json JSONB NOT NULL DEFAULT '{}'::jsonb,

  accepted_by_user_id UUID NULL REFERENCES users(id),
  accepted_at TIMESTAMPTZ NULL,

  revoked_at TIMESTAMPTZ NULL,
  revoked_by_user_id UUID NULL REFERENCES users(id),

  expires_at TIMESTAMPTZ NULL,

  last_invited_at TIMESTAMPTZ NULL,
  invite_count INT NOT NULL DEFAULT 1,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  CONSTRAINT chk_partner_seats_scope
    CHECK (
      (event_id IS NOT NULL AND series_id IS NULL)
      OR
      (event_id IS NULL AND series_id IS NOT NULL)
    )
);
Notes
exactly one scope must be assigned: either event_id or series_id
status values for MVP:
invited
active
expired
revoked
removed
permissions_json stores resolved permissions snapshot at time of invite
7.2 seat_invites

Represents tokenized invite records. One seat may have multiple invite sends over time.

CREATE TABLE seat_invites (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  seat_id UUID NOT NULL REFERENCES partner_seats(id) ON DELETE CASCADE,

  token_hash TEXT NOT NULL,
  sent_to_email CITEXT NOT NULL,

  sent_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  expires_at TIMESTAMPTZ NOT NULL,
  accepted_at TIMESTAMPTZ NULL,
  revoked_at TIMESTAMPTZ NULL,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
Notes
store only token hash, never raw token
raw token appears only in invite email link
each resend should generate a new token
previous live tokens should be invalidated when resend occurs, unless deliberately allowing multiple valid tokens; MVP should invalidate previous pending tokens
7.3 user_event_access

Represents active, accepted access rights for a user.

CREATE TABLE user_event_access (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  partner_id UUID NOT NULL REFERENCES partners(id) ON DELETE CASCADE,

  event_id UUID NULL REFERENCES events(id) ON DELETE CASCADE,
  series_id UUID NULL REFERENCES event_series(id) ON DELETE CASCADE,

  seat_id UUID NOT NULL REFERENCES partner_seats(id) ON DELETE CASCADE,
  role_code VARCHAR(100) NOT NULL,
  permissions_json JSONB NOT NULL DEFAULT '{}'::jsonb,

  status VARCHAR(50) NOT NULL DEFAULT 'active',

  granted_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  removed_at TIMESTAMPTZ NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  CONSTRAINT chk_user_event_access_scope
    CHECK (
      (event_id IS NOT NULL AND series_id IS NULL)
      OR
      (event_id IS NULL AND series_id IS NOT NULL)
    )
);
Notes
one active row per user + seat
permissions are copied here so historical seat edits do not silently rewrite prior access without an explicit update action

10. Backend Endpoints

All endpoints below assume authenticated partner/admin context unless otherwise stated.

10.1 Create Seat Invite
POST /api/partner-seats/invite

Creates a seat and sends an invite email.

Request
{
  "partnerId": "uuid",
  "scopeType": "event",
  "eventId": "uuid",
  "seriesId": null,
  "invitedName": "Sarah Miles",
  "invitedEmail": "sarah@example.com",
  "roleCode": "guest_list_manager",
  "note": "You’ll be helping manage guest arrivals for this session."
}
Validation
user must have permission to manage partner seats
scopeType must be event or series
exactly one of eventId or seriesId must be provided
email must be valid
role code must be one of allowed templates
scope must belong to the partner
cannot create duplicate active/pending seat for same email + same scope + same role unless explicitly allowed; MVP should block duplicates and return useful message
Response
{
  "seat": {
    "id": "uuid",
    "status": "invited",
    "partnerId": "uuid",
    "eventId": "uuid",
    "seriesId": null,
    "invitedName": "Sarah Miles",
    "invitedEmail": "sarah@example.com",
    "roleCode": "guest_list_manager",
    "permissions": {
      "can_view_event_summary": true,
      "can_view_attendees": true,
      "can_check_in_guests": true,
      "can_invite_guests": true
    },
    "expiresAt": "2026-05-01T23:59:59Z",
    "createdAt": "2026-04-23T15:00:00Z"
  }
}
10.2 List Seats for Scope
GET /api/partner-seats?partnerId=...&scopeType=event&eventId=...

Returns all pending/active/revoked/expired seats for that scope.

Response
{
  "items": [

      "acceptedByUserId": null,

}
10.3 Resend Invite
POST /api/partner-seats/:seatId/resend

Generates a fresh token, invalidates previous pending tokens, sends new email.

Request
{
  "note": "Resending this in case you missed the first email."
}
Validation
seat must belong to partner
seat status must be invited or expired
cannot resend revoked or removed seats
rate limit resend, e.g. once every 60 seconds
Response
{
  "success": true,
  "seatId": "uuid",
  "status": "invited",
  "lastInvitedAt": "2026-04-23T15:10:00Z",
  "expiresAt": "2026-05-01T23:59:59Z"
}
10.4 Revoke Invite
POST /api/partner-seats/:seatId/revoke

Revokes a pending invite before it is accepted.

Response
{
  "success": true,
  "seatId": "uuid",
  "status": "revoked"
}
10.5 Remove Active Seat
POST /api/partner-seats/:seatId/remove

Removes active access from an already accepted co-host.

Behavior
mark partner_seats.status = removed
mark user_event_access.status = removed
set removed_at
revoke future access immediately
Response
{
  "success": true,
  "seatId": "uuid",
  "status": "removed"
}

13. Auth / Security Rules
MVP Security Rules
invite tokens must be random, long, and single-use
store token hashes only
acceptance requires authenticated account
authenticated account email must match invited email exactly
invite acceptance cannot escalate privileges beyond assigned seat
seat access must be scope-restricted
all changes must be audited
partner can only manage seats for their own scope
only authorized partner admins can create seats
old tokens invalidated on resend
14. Business Rules
Only Partner Admin can create co-host seat invites in MVP
One seat must belong to exactly one scope:
event OR series
A seat is not access until it is accepted
A seat invite can exist for a non-user email
Acceptance creates or links a user account
Accepted account must match invited email
Resend generates new token and updates expiry
Revoke blocks future acceptance
Remove Access disables active access immediately
Co-host cannot modify event structure, pricing, or payout settings in MVP
15. Edge Cases
Duplicate invites

If same email + same role + same scope already has a pending or active seat:

block duplicate creation
return existing seat info
suggest resend instead
Existing user already on platform

If invited email already belongs to existing user:

still send invite
on accept, user signs in and seat activates normally
Wrong-email login

If user clicks invite but signs in with another email:

do not allow acceptance
show explanatory message
Invite accepted after revoke
reject with revoked status
Invite accepted after expiry
reject with expired status
Partner changes mind after acceptance
remove access endpoint used
access disappears immediately
Multiple pending tokens

MVP should invalidate prior pending tokens when resend happens

Deleted event or series

If scope is deleted before acceptance:

mark seat revoked or invalidated
show unavailable message on acceptance page
