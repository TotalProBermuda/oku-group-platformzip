For `provisionHostPersonalReferrer`, the create/reactivate paths call `ensureHostReferralActor(..., tx)`. If dedupe returns `merge_required`, the dedupe service’s canonical `referral.actor.merge_required` audit row is written inside the same transaction, then `HostMergeRequiredError` is thrown to roll back the assignment create/reactivation.

That rollback likely also rolls back the canonical `referral.actor.merge_required` audit row.

The follow-up `host.me.referral_actor_conflict` audit helps, but it is not the canonical action #170 will read, and it lacks the full canonical fields (`candidateActorUserId`, `matchField`, etc.).

Fix:
After catching `HostMergeRequiredError`, write a non-transactional canonical `referral.actor.merge_required` row, or change the sentinel to carry enough metadata and write both:
- canonical `referral.actor.merge_required`
- optional `host.me.referral_actor_conflict`

Do not rely on an audit row written inside a rolled-back transaction.

P1 — Existing ACTIVE assignment conflict still leaves an active unbridged assignment.
The new transaction fix covers create/reactivate. But if `existingAny.status === ACTIVE`, the code intentionally does not transaction/rollback, and a merge conflict returns `{ ok:false }` while the active assignment remains active.

If that assignment is already unbridged and conflicting, this can still produce the “active QR assignment exists but identity unresolved” state.

Options:
- on merge_required for an existing ACTIVE personal assignment, mark it non-active/blocked/invited until resolved, or
- explicitly prove the page/API suppresses use of that assignment whenever `provisionFailed` is true.
