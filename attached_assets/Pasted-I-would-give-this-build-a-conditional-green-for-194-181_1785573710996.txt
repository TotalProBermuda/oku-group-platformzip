Remaining Red-Team Risks
[P0] Need proof that the QR mobile flow is actually usable.
The report says the Reserve tab works, but we need screenshots/video at 390px mobile showing the complete flow:
Scan QR → Reserve → Date → Time → Party Size → Space → Guest Info → Submit → Confirmation
If date/time/space sit too low in the form, the booking party may still miss them.
[P0] Host dashboard must show the new booking context immediately.
When a guest submits, the host card must show:
reservation date/time
party size
requested space
referrer/source
availability/over-capacity signal
quick action: confirm / modify / assign table
If the host still only sees a generic queue item, the system is not operationally ready.
[P0] Space availability is not table/floor readiness.
The new API returning 4 spaces is good, but restaurant service needs:
Space → Table → Chairs → Assigned reservation → INVU binding
Space-level capacity prevents obvious overbooking, but it does not yet give the host a true floor-control workflow.
[P0] INVU binding remains the commission-proof gate.
This build does not appear to solve:
seated reservation needs “Bind INVU Table” notification
unbound seated reservation cannot be closed into commission proof
wrong INVU binding recovery
INVU table/check ID stored against reservation
That should be the next P0 after guest booking.
[P1] Availability must match reservation duration.
The availability endpoint must use overlapping windows, not just date/time slot labels. Confirm the chosen time slot maps to a real service window, e.g. 7:00–9:00. Otherwise 7:00 and 8:00 can overbook the same seats.
[P1] Requires-approval spaces need distinct UX.
If Catch, Terrace, or VIP requires host approval, the guest confirmation should say:
“Request received” / “Pending confirmation”
not:
“Reservation confirmed.”
[P1] No-space / full-capacity state must be beautiful and useful.
If no space can fit the party, do not dead-end the guest. Offer:
choose another time
choose another date
request host review
WhatsApp the restaurant
[P1] Profile sync still needs matrix testing.
This must work from every QR source:
Sophia influencer
taxi referrer
partner
generic referrer
newly created referrer
The destination flow should be identical except for profile-specific branding/source attribution.
