#98 — Privacy, Security & Trust UX Assessment for Beneficiary/Payout Platform

What & Why
#97 maps Panama Law 81, data classification, lawful basis, cross-border processors, and the privacy roadmap. The next step is to assess what privacy/security/trust functionality already exists in the OKÜ platform and design the actual user experience for the implementation phases.

This task should not build the full privacy system yet. It should assess existing code, identify reusable pieces, and produce a modern, mobile-first UX plan for the beneficiary verification, payout-readiness, privacy controls, and trust surfaces.

The goal is to avoid bolting privacy onto the platform as legal text. Privacy should become a product experience: clear, secure, confidence-building, and easy for referrers, partners, beneficiaries, finance admins, and Superadmins to use.

Context
OKÜ is now collecting or preparing to collect:
- beneficiary bank information
- payout verification details
- ID / tax / RUC status
- proof-of-address status
- source-of-funds status
- payout rules
- payout eligibility states
- finance/admin review notes

This is restricted compliance data. It must be protected and also explained clearly to users.

UX Standards
The UI plan must be:
- mobile-first for referrers/influencers/partners
- simple enough for non-technical users
- finance-grade for admins
- clear about what is verified and what is pending
- clear that OKÜ performs beneficiary verification, while Banesco performs formal bank/KYC/AML
- beautiful, modern, calm, and trust-building
- not a wall of legal text
- not generic compliance software
- consistent with OKÜ’s premium hospitality brand
- minimalist but not empty
- operationally useful, not decorative
- designed for speed, reassurance, and clarity

Modern Minimalist Functional UI Specification
The UX plan must define a visual and interaction system for future implementation.

Design Principles:
1. Calm confidence
   The UI should reduce anxiety around money, bank details, and identity verification.
   Avoid alarming language unless action is truly blocked.

2. One decision per screen
   Especially on mobile, each step should ask for one logical group of information only.

3. Visible protection
   Users should always know why information is requested, how it is protected, and what happens next.

4. Status before detail
   Every screen should first answer:
   - Am I verified?
   - Can I be paid?
   - What is blocking me?
   - What action do I need to take?

5. Progressive disclosure
   Do not show dense compliance detail unless the user asks or the admin needs it.

6. No false certainty
   Distinguish:
   - OKÜ verified
   - bank-ready
   - Banesco formal KYC/AML
   - payout eligible
   - payout paid

7. No raw sensitive data
   After save, sensitive fields appear masked only.

Visual Style:
- Premium, quiet, hospitality-grade.
- White or warm off-white backgrounds for finance/admin surfaces.
- Deep charcoal or OKÜ dark surfaces only where already established for earner dashboards.
- Restrained OKÜ red for primary actions.
- Green only for verified/paid/success.
- Amber for pending/review/needs attention.
- Red only for rejected/blocked/security risk.
- Avoid loud gradients, decorative blobs, or busy illustrations.
- Use cards only for distinct repeated items, review blocks, or mobile step panels.
- Do not nest cards inside cards.
- Keep radius subtle: 6–8px max unless existing system says otherwise.
- Dense admin tables are acceptable on desktop; avoid dense tables on mobile.

Typography:
- Clear hierarchy:
  - Page title
  - Status summary
  - Action instruction
  - Supporting explanation
- Avoid long legal paragraphs in primary flow.
- Use plain language:
  “Complete payout verification”
  not
  “Submit compliance documentation.”
- Button labels should be action-specific:
  “Submit for review”
  “Request changes”
  “Approve beneficiary”
  “Place payout hold”
  “Add bank details”
- Do not use tiny compliance disclaimers as the only privacy notice.

Mobile Layout Rules:
- Design first for 375px width.
- Single-column flow.
- Sticky bottom action bar for long forms.
- Large touch targets, minimum 44px height.
- Progress indicator always visible during verification.
- Manual save reassurance:
  “Saved securely”
  “Masked after saving”
- Show only one primary CTA per screen.
- Secondary actions should be text buttons.
- Avoid horizontal scrolling.
- Avoid tables; use stacked rows/cards.
- Error messages appear inline directly under the affected field.
- Blocking status appears at top as a clear summary.
- Manual support path always visible.

Admin Layout Rules:
- Desktop-first, but responsive.
- Queue view with filters, tabs, and search.
- Drawer detail for review.
- Masked sensitive fields by default.
- “Restricted compliance data — access is logged” banner at top of drawer.
- Review checklist in right rail or top summary.
- Eligibility blockers clearly grouped:
  - Identity
  - Bank readiness
  - Compliance hold
  - Threshold
  - Reconciliation
  - Payout cadence
- Audit trail visible but not visually dominant.
- Approval/rejection actions require confirmation.
- Reject/request-changes requires a reason.
- Hold requires a reason.
- Approve action disabled until required checks pass.
