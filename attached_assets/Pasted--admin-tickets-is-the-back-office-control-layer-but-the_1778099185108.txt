Use this revised task:

Implement Ticket Operations P0 — Mobile-first QR check-in + website ticket control.

The QR check-in experience must be as smooth and mobile-first as the Referrer QR interface. Door staff will likely use a phone camera at the venue entrance. The interface must be fast, simple, and resilient under pressure.

Scope:
Website-issued tickets only:
- tickets created from paid website orders
- manually issued comp/admin tickets

Do not include:
- POS/INVU table payments
- restaurant table sessions
- RFID wristbands
- external ticketing integrations
- two-way sync with payment gateway

Core workflow:
Website checkout → paid order → ticket issued → QR code scanned at door → ticket marked checked-in.

Check-in is one-way internal state:
- QR scan updates Ticket / ExperienceCheckin / CheckInLog / AttendanceEvent.
- It does not update Authorize.net.
- It does not update INVU.
- It does not affect commissions except where existing ticket/order attribution already exists.

ROLES / PERMISSIONS

Add explicit permission:
- admin:tickets:read
- admin:tickets:write
- tickets:checkin

Permission rules:
- SUPERADMIN: all ticket permissions
- ADMIN_COMMERCIAL or general ADMIN role if present: admin:tickets:read, admin:tickets:write, tickets:checkin
- RESTAURANT_HOST: tickets:checkin
- STAFF_OKU if appropriate: tickets:checkin
- STREETSIDE_HOST only if product owner confirms; otherwise do not grant by default

Important:
Do not require Superadmin for staff scanning.
Restaurant hosts must be able to use /staff/check-in.

  Superadmin/Admin ticket search, detail drawer, manual issue, export.

Staff/mobile:
- /staff/check-in
  Mobile-first scanner interface for authorized hosts/admins.

MOBILE-FIRST STAFF CHECK-IN UX

/staff/check-in must be redesigned/polished as the primary venue door experience.

Design goals:
- mobile-first
- one-handed use
- high contrast
- fast scan feedback
- minimal text
- large action buttons
- works at venue entrance in poor lighting
- no admin console clutter
- no large tables
- no desktop-first layout

/staff/check-in layout:

1. Top bar
- OKÜ logo
- current role/user
- selected session/event
- small status dot: Ready / Camera off / Offline / Error

2. Session selector
- If host has multiple sessions today, show a compact selector.
- Default to today’s active/upcoming session.
- Show:
  - event/series name
  - session time
  - checked-in count / total tickets

3. Scanner hero
- Large camera scan area.
- Rounded but not playful.
- Primary action:
  - Start scanning
  - Pause scanner
  - Resume scanner
- Torch button if supported.
- Camera switch button if supported.
- Manual code entry button.

4. Scan result state
After scan, show a full-width result panel:

Success:
- green state
- “Checked in”
- guest name
- ticket type
- party/session
- timestamp
- haptic/audio feedback if easy and safe

Already checked in:
- amber state
- “Already checked in”
- original check-in time
- guest name
- staff can dismiss and continue scanning

Invalid / refunded / cancelled:
- red state
- clear reason
- no check-in mutation
- staff can dismiss and continue scanning

5. Manual fallback
- Search/input ticket code, guest name, or email.
- Show matching ticket.
- Manual check-in button if permitted.
- Must write CheckInLog with method ADMIN_OVERRIDE or MANUAL.

6. Recent scans
- Last 5 scan attempts only.
- Compact chips:
  - guest
  - result
  - time
- No large table.

7. Offline / poor connectivity behavior
For P0:
- Do not implement offline queue unless already easy.
- Show clear “Connection required” state.
- Disable scan mutation if API unavailable.
- Avoid pretending offline check-ins are saved.

8. Accessibility
- Buttons minimum 44px height.
- Text legible on phone.
- No tiny icon-only controls without labels.
- Result states should not rely on color only.

STAFF CHECK-IN API SAFETY

On QR scan:
- Look up Ticket.code.
- Confirm ticket exists.
- Confirm ticket belongs to selected session or warn if different session.
- Confirm order is PAID OR ticket is valid comp/manual-issued.
- Confirm ticket is not refunded/cancelled.
- Confirm not already checked in.
- On success:
  - update Ticket.checkedInAt
  - update Ticket.checkedInById
  - create ExperienceCheckin
  - create AttendanceEvent if existing pattern supports it
  - write CheckInLog result VALID
- On failure:
  - write CheckInLog with INVALID / EXPIRED / ALREADY_CHECKED_IN / CANCELLED / REFUNDED as applicable
  - do not mutate Ticket checked-in fields
