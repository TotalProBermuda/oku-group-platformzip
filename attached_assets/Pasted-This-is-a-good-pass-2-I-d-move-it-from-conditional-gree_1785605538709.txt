Remaining Red-Team Risks
[P1] Frontend pending copy trusts local space state.
The API returns pendingApproval, but the form reportedly decides copy from local selectedSpace.requiresApproval. Use the API response as the source of truth after submit. Otherwise stale client state could show “Booking submitted” when the server actually created PENDING_APPROVAL.
[P1] Full-capacity fallback must not block “host review” logic.
For premium hospitality, “full” should not always mean “impossible.” Add or confirm a fourth path:
Request host review / Join waitlist / Ask concierge.
WhatsApp helps, but a trackable in-system fallback is better for ProofPay’s ledger.
[P1] Status naming must be consistent across host filters.
If the API creates PENDING_APPROVAL, make sure host dashboard counts and filters include it. If the board only expects PENDING, CONFIRMED, ARRIVED, etc., pending approval reservations could disappear from the working queue.
[P1] Capacity and approval logic need to combine cleanly.
If a space is both available and requiresApproval, it should be selectable with clear copy:
“Request this space” rather than “Reserve this space.”
If it is unavailable and requiresApproval, the UI needs to clarify whether the guest can still request review.
[P2] WhatsApp fallback number should be configurable.
Hardcoding 50764316090 is okay for a pilot, but this should become venue config before multi-market rollout.
